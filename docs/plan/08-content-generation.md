# 08 · Content generation

Rule: **code controls difficulty, the LLM writes content, code checks it.**

## Who does what

| Step | Done by | Example |
|---|---|---|
| Pick difficulty | Scorer (`07`) | b = 0.4 for Market Rush |
| Turn difficulty into knobs | Game `level_map` | 3 customers, 4 items each, 20% change rate |
| Write content | LLM, strict JSON | Customer names, items, short lines ("Two kilos of oranges, and some chilli") |
| Check content | Validators | Count, duplicates, word list, solver, novelty |
| Serve | Game plugin | Runs the jsPsych timeline |

Games that need no language (n-back sequences, reaction time, Corsi) are generated by code from a seed. No LLM, no delay.

**As built (WP2.2).** For every content game, code builds the whole structure from the seed and knobs (orders, word lists, matrices, worked solutions with the planted error), with plain template text, and that version always passes the validators. The LLM is only asked to make the words nicer: Market Rush customer lines, Market List words for a theme we have no list for (UW4), Pattern Gap hint ladders, Spot the AI's Mistake step wording. Its answer is merged into the structure and validated; on failure it is repaired up to twice, then a pool item is used, then the code-built version. Served items are recorded in `agent.content_pool`, `agent.content_served` and the user's Qdrant `exercises` points (novelty). Code: `backend/generation/` (`generators/`, `pipeline.py`, `pool.py`, `prompts/`); vocabulary in `registry/content/themes.yaml`.


## Schemas

Every generator has a Pydantic schema, and the LLM is called with structured output against it.

```python
class MarketOrder(BaseModel):
    customer: str = Field(max_length=20)
    line: str = Field(max_length=120)
    items: list[str] = Field(min_length=1, max_length=6)

class MarketRushContent(BaseModel):
    theme: Literal["fruit", "spices", "bakery", "pottery", "mixed"]
    orders: list[MarketOrder]
    changes: list[OrderChange] = []
```

## Validators

Run in order; any failure triggers a repair or fallback.

1. **Schema:** parses, right counts for the requested knobs.
2. **Content rules:** no duplicates within a round; words from an allowed vocabulary when the game needs common words; length limits.
3. **Language filter:** no clinical words, nothing unsafe (`09`).
4. **Solver:** for puzzles (matrices, logic, Tower, mazes, Spot the AI's Mistake), a program checks there is exactly one correct answer and, for Spot the AI's Mistake, that the planted error is really an error.
5. **Novelty:** embed the content and search the user's `exercises` collection in Qdrant; reject if cosine > 0.9 to something served in the last 30 days.

## Repair loop

```
generate → validate ─ ok → serve
               └─ fail → repair (send errors back to the LLM) → validate
                                    └─ fail twice → take from pool
```

## Pools

- A background job keeps the `agent.content_pool` table filled (target: 30 items per game and level for P1 games); `agent.content_served` stops a user from getting the same item twice.
- Pool items went through the same validators.
- Play never waits on an LLM call.

## Pattern Gap (matrices) generation

LLMs are bad at making valid visual puzzles, so we don't ask them to. A program generates matrices from rules (rotation, count, colour progression, XOR of shapes), with the number of rules setting difficulty. The LLM only writes the hint ladder text. The solver confirms one correct option among the distractors.

## Spot the AI's Mistake generation

1. The program generates a puzzle and its correct solution steps.
2. With probability 0.7 the LLM is asked to introduce **one** subtle error in a chosen step type (arithmetic slip, wrong rule, skipped case); otherwise the solution stays correct.
3. The solver re-runs the steps and confirms the error (or the absence of one).
4. The user must flag the error or confirm the solution is right. Both are scored (`11`).

The consent screen discloses that Lodestar will sometimes show deliberately wrong reasoning in this game.

## Custom games from blocks (user asks for a new game)

The user says, for example: "Give me a game where I remember a phone number while doing maths."

1. The LLM writes a **recipe** using only known blocks. It never writes code.
2. Code validates the recipe (known blocks, sane timings, max 3 minutes, scorable).
3. The block engine runs it as a jsPsych timeline.
4. Scores count with `reliability` 0.3–0.5 (`07`), and Lodestar says so: "Fun game. I'm only counting it a little until it's been tested more."

### Blocks

| Block | Does |
|---|---|
| `show_items(items, ms_each)` | Flash items |
| `distractor(task, seconds)` | A filler task (maths, tapping) |
| `recall(kind)` | Free recall, ordered recall, or recognition |
| `choice(question, options, answer)` | Multiple choice |
| `timer(seconds)` | Countdown |
| `rule(rule_text, switch_after)` | A rule that may change |
| `react(target, distractors, deadline)` | Speed response |
| `feedback(level)` | Show result |

### Recipe example

```json
{
  "title": "Number and Numbers",
  "dims": {"working_memory": 1.0},
  "steps": [
    {"block": "show_items", "items": "digits:7", "ms_each": 800},
    {"block": "distractor", "task": "arithmetic:easy", "seconds": 15},
    {"block": "recall", "kind": "ordered"}
  ],
  "repeat": 3
}
```

**As built (WP3.7).** One generic registry entry, `custom_blocks` ("Custom Game", origin `custom`, reliability 0.4), never picked by the policy or used in experiments; it is served only when asked for ("make me a game where...", a rule in `backend/agent/intents.py`). The recipe schema and validator are `backend/generation/blocks.py` (the source of truth): a Pydantic union of the eight blocks with bounded timings, plus rules for known ability skills with one at 1.0, recall only after something was shown, answers among the options, at least one scored block, and an estimated length of at most 180 s; then the clinical-language filter. Two blocks are narrower than the table above so they can be run and scored: `rule` is `odd_even` or `high_low` (with `switch_after`) rather than free text, and `show_items` takes `"digits|letters|words|shapes:N"` or an explicit list (listed items and digits are recalled in order only). The pipeline treats it as a content game (`generators/custom_blocks.py`, prompt `custom_blocks.md`): the user's words are the brief, the LLM's recipe is validated and repaired, and on failure a starter recipe from code is served; novelty checks are skipped (items are drawn fresh from the seed every round). Each round stores its recipe's skills in `twin.rounds.loadings` (migration 0006), so it counts for those skills at loading x 0.4. The browser engine is `frontend/src/games/custom_blocks/` (`engine.ts` turns a recipe into one jsPsych item per block per repeat through `makePlugin`). The "Done when" check: `python -m backend.generation.recipe_samples` writes `tests/fixtures/custom_recipes.yaml` (50 recipes from a model with `--local` or `--user/--provider/--model`; without a model, a seeded set that mimics model output, with 20 broken on purpose in 15 different ways). `tests/backend/generation/test_custom_blocks.py` checks every invalid one is rejected and serves one through the graph; `engine.test.ts` builds every valid one and plays it to the end in jsPsych.

## Prompts

Prompts live in `backend/generation/prompts/<game>.md`, with versions. Every generation logs the prompt version, model, seed and validator results to the trace.
